# Trainer NPU 精度开关修复：独立验收约束

起点：`hf1s/hyper-parallel:JT_dev`，`f637ef7ee4d4b416800716f1ebaaae7709b8a06a`。

实际缺陷：`enable_high_precision_for_bf16()` 在 NPU 分支写入 CUDA 风格的两个属性，已安装 TorchNPU 2.12.0 对这些名称不处理。若调用者已开启 HF32，Trainer 初始化后仍开启。默认读回是关闭，不能把该缺陷归因于现有 EP2/CP2 的精度失败。

要求：

1. NPU 高精度策略通过受支持的 `torch.npu.matmul.allow_hf32` 关闭 HF32；删除无效属性写入。
2. 保留函数签名、调用时机和 CUDA 的 TF32/BF16 reduction 策略；CPU 无需任何加速器选项接口。
3. 文档区分 NPU FP32 matmul 的 HF32 控制与 BF16 累加，不能声称后者已被该接口控制。
4. 单元测试不能分配 NPU/GPU，覆盖 HF32 原来开启/关闭、CUDA 与 CPU 分支。同一用例必须在旧源码失败、修复源码通过。
5. 真实 TorchNPU 选项的读写验证允许在无设备容器中强制选择 NPU 条件分支；需要明确这种验证不等于硬件 matmul/200 步训练验证。
6. 独立 PR 只包含生产文件和对应 UT，单提交；与总单 #202 关联的小问题单、PR 均中文详细，保持草稿，不宣称 CI 或跨拓扑精度验收通过。

证据根目录：`../evidence/` 下 `npu-precision-*`。初版 CPU 批次的测试本身完成，尾部读取 stdout 重定向文件时被底层驱动诊断文本干扰，批次返回 1；保留该日志。改为独立 JSON 文件输出后，`npu-precision-option-after-v2` 无设备容器退出 0、已移除，真实开关读回验证通过。不得把初版整个批次说成 exit 0。
