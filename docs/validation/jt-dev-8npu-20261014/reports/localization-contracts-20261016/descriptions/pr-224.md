**What does this PR do / why do we need it**:

父进程限定 `ASCEND_RT_VISIBLE_DEVICES=4,5,6,7` 后，`parallel_run` 原先仍将两个两卡用例分配到 `0,1` 和 `2,3`，`run_case` 随后把错误编号写入 worker 环境。现在从父进程的可见列表中按顺序分配 `4,5` 与 `6,7`，每组互不重叠；实际预算同时受可见数量和 `global_num_proc` 限制。

在端口分配或进程启动前校验预算、每个用例的正整数进程数，以及可见列表的格式、唯一性和升序要求。非法输入明确报 `ValueError`，不会回退到全部设备。未设置该环境变量时保留零起始分配；CPU 模式继续忽略 NPU 可见列表并清除 worker 中的该变量。父进程环境不会被切片过程改写。

变更范围只有 `tests/common/parallel_case.py` 和对应的 `tests/ut/common/test_parallel_case.py`，独立一个提交。没有修改模型、通信算子、loss、优化器或 checkpoint。启动器仍不加载训练框架，也不调用设备 API 探测实际硬件。顺便将同一函数既有的超时说明从误写的 900 秒更正为代码现有的 420 秒 join timeout；超时和终止行为本身未改动。

基点为 `hf1s:JT_dev@f637ef7ee4d4b416800716f1ebaaae7709b8a06a`，已包含 #180。与 #214 的不均匀分片拒绝逻辑无依赖关系；本项是在为该 PR 准备受限设备回归时单独发现的测试启动器问题。
